# 工作流自我迭代方案

日期：2026-11-10。状态：建议方案，尚未接入运行流程或创建定时任务；现有 GitHub 提交和 V0.2 ZIP 不包含此能力。

## 1. 目标与当前缺口

让 AI 在推进客户游戏的同时，识别协作中的困难，改进本项目的 skills、操作卡、模板、提示词和必要工具，验证改动，再观察后续使用效果。客户正常表达即可，不承担维护规则、分类问题或填写复盘表的工作。

目前已有游戏反馈、任务审查、变更与交接，但尚无独立的工作流改进记录、复盘触发、行为回归与效果追踪。游戏完成进度仍以 state.json 为唯一权威；工作流改进不计入游戏任务完成率。

TopDown 的现有文件体现了从具体问题固化规则的方式：分开检查正确性和必要性、核对真实调用、区分静态与运行证据。历史改进也包括删去过重流程、按风险决定工作量。本方案复用这种方法，具体游戏技术与客户职责仍遵循当前新手项目。

## 2. 推荐组合：及时纠正、任务复盘、定期整理

| 触发 | AI 要做什么 | 运行时机 |
|---|---|---|
| 明确反馈 | 发现“已经说过了”“看不懂”“不要总问我”“这个步骤根本没有”等纠正，先解决当前困难，再判断是否存在工作流缺陷 | 当前协作中立即处理，不等周报 |
| 客观异常 | 同类工具失败、反复重开任务、交接缺步骤、重复提问、证据/网页不一致等，进入候选问题 | 由当前任务已有日志和事件提供线索 |
| 任务收尾 | 轻量核对本次纠正、返工、哪些做法有效；保存新发现和来源，检查已试改进是否再遇到相似场景 | guide 的任务收尾必经步骤；没有新信号就不写空复盘 |
| 阶段/周期复盘 | 合并重复问题、找共同原因、安排少量高收益改进、移除过时或冲突规则 | 建议每完成 5 个任务、阶段验收或距离上次复盘 7 天且有新增材料时触发；具体频率可调 |

前几种触发由正在工作的 AI 在流程中执行，不意味着网页后台能自主调用模型。若未配置定时运行，到期复盘在下一次打开项目继续工作时执行。可选定时任务用于补查遗漏，不作为基础能力的唯一依赖。

## 3. 收集可核实的信号，不把语气直接判成需求

优先用当前对话中真实可见的客户原话、网页反馈、任务修改与验证记录。记录最小必要信息：来源标识/时间、任务与阶段、原话或明确标注的摘要、AI 当时做法、客户遇到的困难、后续处理和已知结果。

区分：明确指令、偏好、游戏设计变化、操作说明缺口、工具/环境问题、错误实现、尚待核实的推测。客户说“画面不舒服”先处理画面目标；不能直接总结成“以后禁止这种美术风格”。同一问题多次出现是优先调查信号，不自动证明原因相同。

只要有明确纠正或可复现缺陷，一次也可以修；弱信号先局部试用或等待其他证据。客户没有再抱怨不能当作满意，AI 自己的总结也不能升级为客户确认。有效做法同样记录，用于防止改进时破坏已验证的协作方式。

## 4. 历史对话采用增量查证与降级读取

1. 当前可见对话：当场提取必要事实，避免等到历史不可见才补记。
2. 宿主确有对话读取工具时：只读本项目已关联对话，用游标或最后处理项增量读取，保留来源；读取失败、被截断或只拿到摘要时明确覆盖范围。当前宿主提供 read_thread 一类工具，不代表客户安装环境一定提供同样工具。
3. 没有接口时：读取项目内改进记录、网页反馈、任务事件与交接；需要精确还原时再使用客户提供的对话导出。自动发现不到的材料标记缺口，不要求客户每次手工整理聊天。
4. 本地原始会话文件只作为经过路径/格式验证的可选适配；不把固定机器路径写入可移植 skill，也不扫描其他项目来推断当前客户偏好。

建议记录每个来源的读取位置和最后成功时间；以原始事件标识去重。没有可靠标识时记录来源位置，不虚构完整覆盖。扫描到新材料后先落盘再推进读取位置，失败重跑不重复建改进项。

官方 App Server 提供历史分页读取接口，技术上可做更深集成；第一版先使用宿主现成能力，不要求客户搭建额外服务。[官方接口文档](https://learn.chatgpt.com/docs/app-server)

## 5. 从信号到真正的改动

每个候选按以下顺序处理：

1. 核实原场景与原因：到底是说明错误、AI 没执行已有规则、工具限制，还是客户改变目标。
2. 选最小有效修复层：本次操作卡 → 客户项目偏好/规范 → 专门 skill → 共用模板或工具。能修实际说明就不新增抽象管理规则；已有规则没执行时优先补触发、检查或脚本。
3. 记录可观察的预期：例如“下一次无需客户重复世界观，先列已读内容再问缺口”，而非“沟通更专业”。
4. 在安全任务边界更新相关文件，检查冲突、重复和适用范围；不要在同一批次同时改多套机制，使效果无法归因。
5. 执行正确性与必要性审查、原失败情境回归和相关既有案例回归。修改代码/状态协议按现有测试约定执行。
6. 进入“试用中”，在下次实际相似任务观察是否减少卡点；没有遇到对应场景就保持“待观察”。出现反效果，记录原因并回退本次修改。

状态建议：候选 → 已核实 → 修改中 → 试用中 → 有效 / 无效 / 已撤回；另有“暂缓/不适用”与原因。状态不能由“写好了总结”直接跳到有效。

## 6. 自动修改范围

在客户启用本项目持续改进后，下列小范围、可逆改动可由 AI 自行完成并简短告知：补清楚操作步骤、修错链、去重提问、根据已明确偏好调整表达、修正文档冲突、补回归案例、修复已核实的小工具缺陷。相关文件先检查是否有未保存或其他正在进行的修改，发生冲突时保留双方成果，不覆盖。

改变游戏创作方向、承诺范围、预算或客户职责的选择，仍由客户决定。不能为让检查通过而削弱验收、把失败改成成功，或扩大权限；不能因本项目偏好修改全局技能、其他项目或用户全局记忆。改变状态协议或大幅重排工作流时，先形成可审阅方案与迁移/恢复办法。

迭代保留改动前内容、修改范围与验证记录。无 Git 的 ZIP 项目也需有本地备份恢复办法；回退只撤销该次规则改动，不恢复整个旧 state 或覆盖后续游戏成果。内部试用版本与对外发行版本区分，不能每次小修改都自动推送 GitHub、重发 ZIP 或上传客户对话。

## 7. 怎样证明改进有效

建立小型行为案例库，每个实际卡点留下：必要输入、前置状态、预期动作、禁止出现的结果、验证方式。去掉与案例无关的客户原文、身份和故事细节。

例如客户说“我已经写过设定”：应先读可访问资料并标出处；不得重新询问文档明确的内容；确有冲突则聚焦问一个问题。再增加相近但不同的案例，如“资料有两个冲突版本”，避免只对原句反应正确。

验证分层：

- 格式/链接/状态协议：脚本确定性校验；关键约束尽可能放入工具，而非只写“AI 应注意”。
- skill 行为：用原场景及相近场景在新上下文中验证。若只是同一 AI 桌面推演，明确注明；不能把文件格式通过当行为通过。
- 客户实际效果：后续相似任务的重复解释次数、卡点是否复发、操作能否完成、因说明缺失造成的返工，以及明确客户反馈。小样本只描述实际观察，不制造满意度分数或改进百分比。

每次复盘同时检查规则是否可合并、删除或限定适用阶段。原则是降低客户负担，不以规则数量或“改了多少次”衡量进步。

## 8. 在当前交付包中的实现落点

建议第一版新增一个 `beginner-workflow-improve` skill，由 guide 在明确反馈、任务收尾及阶段复盘时调用。不是要求客户多学一个入口。

| 位置 | 职责 |
|---|---|
| `.agents/skills/beginner-workflow-improve/SKILL.md` | 识别信号、归因、最小修改、回归、观察和退回规则 |
| `02_工作流规范/工作流持续改进.md` | 运行约定、授权范围、触发、证据与效果标准 |
| `项目记录/工作流改进.json` | 改进项、来源位置、读取游标、试用结果的唯一结构化记录；不复制游戏任务进度 |
| `项目记录/工作流改进证据/` | 需要保留的最小案例、验证记录与变更前内容；不默认归档完整聊天 |
| 现有本地网页与状态工具扩展 | 查看“最近为你改进了什么、还在观察什么”；受校验更新，不由网页调用模型 |
| 现有测试目录 | 新增失败情境与关键协议回归；不另造一套平行测试基础设施 |

网页现有反馈需能关联“游戏任务”或“协作方式”，原有数据继续兼容；客户无需懂分类，可以先自然描述，由 AI 判断。工作流反馈不能自动撤销游戏任务验收。原反馈留一处，改进项通过 ID 引用，处理结果可回看。

客户只需看到一句有用说明，例如：“以后会先读你已有的设定，再问文档没有回答的问题；这次已补到流程里，后续会检查是否还重复问。”无新发现时不发空报告，也不频繁让客户批准技术措辞。

## 9. 定时复盘作为可选增强

官方支持定时任务结合 skills；需要访问本地文件时，电脑和应用需保持运行。因此 ZIP 内只能交付配置指引和复盘提示词，不能声称客户解压后定时任务已自动安装。[官方定时任务文档](https://learn.chatgpt.com/docs/automations?surface=app)

建议先跑通当前对话内的捕获、修改和回归，再在客户环境建立每周复盘。定时运行优先整理候选、去重与生成改进建议；需要修改正在开发的规则/代码时排队到下一安全边界。没有新材料就跳过，不为完成定时任务强行找问题。错过运行在下次协作补查，仍按来源位置去重。

通用经验回流到交付包时，先抽取不含客户内容的案例与修复，再按实际授权提交；客户个性化偏好继续留在其项目内。新交付版本升级旧项目时需比较客户本地修改，禁止覆盖其改进记录和当前游戏状态。

## 10. 第一版完成标准

1. 客户一句“不要重复问我写过的东西”，AI 能捕获、核实、修改正确位置并留下验证记录，无需客户指明 skill 名。
2. 客户只改一次美术喜好时，不误写成全局禁止规则。
3. 新对话可继续已记录的改进；读不到旧对话时说明覆盖缺口，不编造原话或漏读状态。
4. 同一反馈/对话被重复读取，不重复创建改进项或反复改规则。
5. 工作流问题不会污染游戏验收；改进不能悄悄降低原有最低门槛。
6. 改动失败可精确回退，客户现有成果不丢；后续未有真实使用时保持“待观察”。
7. 默认对话内闭环可工作；定时能力缺失或电脑关闭不让主流程永久卡住。
8. 无新问题时允许不修改，并可合并或淘汰过时规则。

本轮只做方案分析和落盘；未增加新 skill、修改网页/状态协议、配置定时任务、更新 GitHub 或重打客户 ZIP。实施时优先完成第一版闭环，再追加定时读取适配。
