# V0.2 引导情境复查

方法：同一 AI 对修订后的 skills、规范和客户入口进行桌面推演，检查是否存在明确下一动作。以下均是教学情境，不是已收到客户资料、真实生成素材或运行游戏的记录。状态执行另见自动测试；不得将此文登记为客户游戏 editor/build/player 证据。

| 客户自然语言 | 按修订规则采取的动作 | 不应卡住的位置 |
|---|---|---|
| “世界观我写好了，你看文件就行” | 先清点附件/00_客户资料，读原文并记录版本与来源；复述已有审核工作和矛盾；只问剩余决定 | 不要求重写 GDD，不把未读当未设定 |
| “网页没出来，我不知道什么 Python” | AI 读启动错误、执行预检、选可用解释器；给一个具体动作；缺环境时可先理解资料 | 不丢一串安装术语，不无限让客户重试 |
| “我能看到页面了，然后呢” | 打开 T00 操作卡；AI 登记当前步骤，客户实际反馈，AI 读取答复再审查 | 页面打开不自动将环境或游戏标通过 |
| “内容要做多少，我也不知道” | 从设定与投入提两三个完整体验方案；暂定范围；样本实测后复核批量计划 | 不迫使客户估算制作成本，不把 Demo 当终点 |
| “类似游戏都是怎么让这件事有压力的” | 使用已有参考 skill，围绕具体压力来源查证可观察做法，说明适用性，必要时做可逆对照试验 | 不把竞品形式直接当需求，不整套照搬 |
| “图片提示词有了，可是在哪里做？声音呢” | 单独核对图像/音频工具和账户预算，选 AI 直做、客户操作或授权素材；给回传位置和导入责任 | 未有实际文件就不能算资源完成，声音不被遗漏 |
| “样例不错，剩下怎么做” | 按内容矩阵建实际批次，生成每批操作卡与测试入口；总检查点依赖全部承诺批次 | 不让第二批等“全部内容完成”，不受无关已验收任务阻止 |
| “自动测试报错了，但我试玩没看出来” | 留失败记录；解释触发与影响；修复后明确关联复测；非阻塞接受须有实际客户决定 | 不因测试类别可选就把失败忽略 |
| “改了日志名字，网页还能用吗” | 页面指出对应证据缺口；AI 核实同一文件，repair_reference 修引用并留原因 | 可继续读取/反馈，不需手改 JSON 解锁 |
| “游戏发过了，现在网页打不开” | 反馈待核实，定位环境问题；只重开真实关联任务；保留旧发行快照 | 不把旧游戏交付撤销为从头再做 |
| “想给朋友玩，究竟发哪几个文件” | 给完整构建包和版本清单，实际安装/存档/启动卡；目标设备独立运行后在已有授权内交付 | 不只发 exe，不冒称本地交付已上架 |
| “又没修好，怎么办” | 两次同类失败无新线索时整理日志、最小复现和已试办法；保留可用版与交接，提出明确外部缺口和可继续工作 | 不无休止尝试，不擅自联系或付费求助 |

程序化生命周期夹具覆盖：20 个基线任务加实际制作批次→逐项登记审查与分层证据→本地版本快照→S9 补丁任务→新快照→新增 S5 内容只重开相关检查点。夹具中的证据统一标注 isolated test，不生成任何真实游戏成功声明。

真实客户试用时，重点观察是否能独立完成“放资料、打开卡片、提交反馈、按卡体验”四件事；任何需要额外口头解释的位置，再回填到对应卡片或指南。
