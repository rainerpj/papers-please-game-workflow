# 审查和证据规则

每一步都检查正确性和必要性。文档工作做文档检查，运行行为做对应运行验证；不为低风险文字修改强加全套游戏测试。

## 两轮审查

正确性：实际成果是否满足需求；规则与分支有没有遗漏；引用、场景装配和调用是否真实；测试是否覆盖本次变化。

必要性：是否扩大了范围；是否新建本可复用的能力；客户是否被要求做不必要操作；状态是否维护了两份；文档是否给出实际可执行步骤。

每轮记录检查范围、发现、修复、复查、未验证项。无发现不代表查过所有路径。同一 AI 的两轮审查必须写“分轮自审”；另一审查者或获授权的子代理实际执行后才能称“独立 Review”。关键范围锁定、代表片段和发布候选建议独立 Review。

## 证据分层

| 类别 | 能支持的结论 | 不能扩大成 |
|---|---|---|
| document | 规则或成果经核对 | 已实现/已运行 |
| static | 源码、引用、文件静态检查 | Unity 已编译、玩家能操作 |
| automated | 指定自动测试实际通过 | 全游戏体验通过 |
| editor | 指定 Unity 版本/场景实际验证 | 打包后或其他设备也可运行 |
| build | 生成指定构建包成功 | 包已经独立运行 |
| player | 指定系统设备下独立运行 | 所有设备/平台兼容 |
| customer | 客户明确决定或实际体验反馈 | 未反馈范围也通过 |

每条证据写任务 ID、执行者、时间、版本、步骤、实际结果、文件路径和限制。客户的原话可以作为体验证据，但 AI 要明确对应哪个场景；自然语言足够清楚时不要求技术报告。

## 完整游戏验收

核对完整内容矩阵，不只展示最佳片段。至少包括新玩家教学、正常循环、规则增长、叙事与所有承诺结局、失败和恢复、存档及迁移、设置与退出、文字/音频/输入、目标设备/系统/分辨率、性能与长时间使用、授权清单及交付资料。只验证范围内平台，未承诺的兼容性不凭空增加。

阻塞缺陷必须解决；非阻塞遗留需客户明确接受并记录。系统校验只能拦住缺少记录、缺失文件和前置未完成，不能判断证据是否撒谎，也不能评判游戏是否有趣。最终仍由 AI 核对实际成果，并由客户体验关键节点。
