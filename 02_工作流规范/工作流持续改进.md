# 工作流持续改进

本项目默认启用对话内持续改进，由正在协作的 AI 执行。客户正常描述感受即可，不需要记住技能名、分类问题或填写复盘表。网页只展示记录和待办，不自动启动模型。

## 固定触发

1. 客户明确纠正或出现重复失败：先解决当前问题，调用 beginner-workflow-improve 核实是否属于工作流缺陷。
2. 每个任务收尾：运行 improvement.py show，轻量核对本步纠正、返工、有效做法及待观察项；没有新材料可以跳过，不制造空报告。
3. 阶段检查点通过、累计 5 个任务完成事件，或距集中复盘 7 天且有新材料：下一个安全边界集中复盘，去重、优先解决高收益问题，并删减过时规则。
4. 跨对话继续：读取改进记录与来源覆盖，优先发现中断恢复；旧对话不可读取时从项目内记录继续，不声称完整回顾了历史。

每轮只改有依据且可验证的内容。实时信号也可以立即修复，不必攒够次数。频率默认值由 improvement.py policy 维护；任务复盘不清空集中复盘计数。

## 独立权威与证据

游戏进度仍在 `项目记录/state.json`；工作流改进以 `项目记录/工作流改进.json` 为唯一权威。网页反馈原文仍只留一份，改进记录引用反馈 ID；对话只留最小必要片段/摘要和来源标识。改进项不增加游戏完成率。

信息依次分为来源信号、核实后的原因、可观察的改进目标、实际修改、验证结果、后续观察。客户沉默不等于满意，写完总结不等于改进有效。案例和观察记录需区分原话与推断、同一 AI 自查与新上下文验证。

主引导负责实际调用，改进 skill 负责归因与执行，审查 skill 负责正确性/必要性及证据层次。客户只需看到有意义的变化和仍待观察的部分，不被内部管理细节打断。

## 本地自动改进边界

允许已核实、可逆的小改进：操作说明、项目内 skills、模板、提示词、非核心工具。显著改变体验、规模、预算、客户职责或核心协议时继续原有方案决策流程。禁止降低验收门槛、伪造执行、改用户全局记忆或其他项目；对外提交/推送、上传、发布使用具体已有授权。

修改前检查当前文件和未完成工作，登记范围并备份；修改后封存、两轮审查、原失败案例与相近案例回归，然后试用。恢复先检查后续修改，只撤回这一次的文件改动；不将旧 state 覆盖到当前游戏。无 Git 的客户 ZIP 项目同样适用。

详细状态、CLI 和 payload 见 [改进操作协议](../.agents/skills/beginner-workflow-improve/references/操作协议.md)。案例格式见 [改进案例与观察模板](../05_项目模板/工作流改进案例.md)。

## 可选定时复盘与升级

基础闭环已在对话内启用，不要求配置定时任务。客户需要固定时间运行时，在其实际宿主中检查定时能力，先在普通对话验证提示词，再通过宿主提供的定时工具配置；不能把当前开发者机器的定时任务当成已安装到客户电脑。定时执行优先只整理来源和候选，修改排到与游戏开发不冲突的安全边界。无定时能力或错过运行，下一次继续时补查。

可复制的定时复盘文本见 prompts.json 的 workflow-retrospective；它不自动创建任务。需要本地文件时遵守宿主运行条件；不替客户新增云服务或 API 费用。

升级已在使用的旧包时：先完整备份，读取当前版本、游戏状态、改进记录和本地改动，再合并工具/规则差异。禁止用新包的空 state 或空工作流改进.json 覆盖客户记录。通用经验回流交付仓库前抽出不含客户资料的案例，并按实际授权提交。
