# 完整游戏的开发与交付流程

目标是交付客户确认范围内的完整游戏。原型验证“值得做吗”，代表片段验证“怎样稳定地做”，二者都不能替代全内容、全流程、目标环境和交付验收。减少范围须由客户明确决定，不能把阶段缩水描述为全部完成。

## 阶段与推进

阶段、基线任务和机器执行的最低验证项统一在 [workflow.json](../04_本地进度网页/workflow.json)。网页直接读取此文件；不要在另一处维护相反门槛。

| 阶段 | 关键成果 | 进入下一阶段前要看到什么 |
|---|---|---|
| 准备协作 | 可访问文件、网页和 AI 的记录 | 客户知道怎样继续和反馈；无需先装 Unity 才能讨论设计 |
| 具体体验与参考 | 项目概念、一个典型审核场景、聚焦参考判断 | 角色工作、玩家判断与结果关系明确 |
| 完整游戏范围 | 完整版本范围、内容矩阵、任务与测试映射 | 明确完整游戏的开始、发展与收束，数量由客户确认 |
| 验证核心玩法 | Unity 工程、最小可玩审核循环 | 实际运行验证正常、错误、重复与重开 |
| 完整代表片段 | 统一的视听叙事样本、制作规格 | 客户体验确认，具备批量制作依据 |
| 完整内容制作 | 全部承诺系统、内容和配套功能 | 内容矩阵逐项可检查，代表片段以外的内容已完成 |
| 全流程联调 | 关键分支与结局覆盖、修复记录 | 能走完整游戏，问题分级并有复测 |
| 发布候选版本 | 指定版本的构建包与设备/系统矩阵报告 | 在目标环境独立运行，阻塞缺陷已解决 |
| 发行与交付 | 构建、源文件、说明、授权清单、发行资料 | 按客户约定交付或在授权后上架；两种状态不能混淆 |
| 上线维护与迭代 | 反馈受理、补丁、回归、备份恢复与交接 | 明确支持边界和负责人，真实事件或明确标注的演练闭环 |

最低验证项不替代具体任务验收；例如全内容制作还必须核对完整内容矩阵。阶段中的汇总检查点以配置 checkpoints 为准，正式开发需要由 AI 新增细分任务，不让一个“完成所有内容”掩盖未完成工作。

## 每一步的固定闭环

读取现状 → 明确这一小步的可观察结果 → 解决必要选择 → 执行 → 正确性审查 → 单独必要性审查 → 相称验证 → 修复复查 → 登记真实证据 → 引导下一步。

默认每轮只处理一个可验收目标。允许先探索后续问题，但不能越过依赖宣称验收；卡住时说明缺什么，继续可独立处理的内容。

## 贯穿各阶段的工作

竞品参考随疑点触发；叙事与美术不是程序做完后才加入；完整内容矩阵、风险、来源和测试随制作更新。存档、文本可读性、设置、目标平台和发布要求须在范围阶段明确，再进入相关开发。发行条款等易变信息到执行时核验。

维护没有永远“全部完成”的日期：本轮以约定的维护交接或已知问题闭环为终点，后续版本新增任务。正式发布、消费和外部上传必须具有明确授权。
