# 进度唯一来源与更新方式

`项目记录/state.json` 保存任务、证据、两轮审查、反馈和操作历史；`04_本地进度网页/workflow.json` 定义阶段和最低门槛。需求内容属于 Markdown 设计文件，状态属于 JSON，互相引用不各写一份完成率。

## 面向 AI 的操作

在项目根目录执行。客户不需要编辑 JSON。

```text
python 04_本地进度网页/workflow.py show
python 04_本地进度网页/workflow.py validate
python 04_本地进度网页/workflow.py apply --payload 项目记录/本次更新.json
```

本机有共享 runtime 时优先通过其 python.ps1 启动；客户机器使用自己安装的 Python 3.10+。payload 必须由结构化 JSON 写入文件，不用字符串拼接 shell。每次先读当前 revision，保存冲突后重新读取并合并，不盲目重试旧版本。

## 更新任务

以下为格式示例，不能直接作为真实证据使用。先创建实际记录文件，再填写实际时间、执行人和结果。

```json
{
  "revision": 0,
  "op": "update",
  "task": "T00",
  "status": "review",
  "blocker": "",
  "evidence": [{"kind":"document","result":"pass","path":"项目记录/测试与问题记录.md","note":"本次实际核对的内容及限制","by":"执行人","at":"实际执行时间"}],
  "reviews": {
    "correctness":{"result":"pass","path":"项目记录/阶段审查记录.md","note":"检查范围和结果","by":"审查人","at":"实际时间"},
    "necessity":{"result":"pass","path":"项目记录/阶段审查记录.md","note":"必要性检查结果","by":"审查人","at":"实际时间"}
  }
}
```

状态：pending 未开始、active 进行中、blocked 遇到阻碍、review 等待验收、done 已验收。blocked 要写 blocker。需要客户决定时，用 update 的 question 字段写一个具体问题和少量选项，首页会显示；客户回答后，AI 更新决策记录再清空 question。反馈保存本身不会清空问题。done 需要前置阶段和依赖完成、两轮通过的审查、全部 required 类别的最新证据通过、所有已登记失败已明确复测解决或有可查处置、无阻碍、无待回答问题与未处理问题反馈。阶段最低项不可删除，风险需要时可在 required 增加类别。

证据类别为 document/static/automated/editor/build/player/customer。必需类别以最后登记结果为准；所有类别的失败都必须逐条处理。新的 pass 用 resolves 数组列出已解决的失败证据零起始索引，例如 [0]；不能仅追加一个不相关的通过就掩盖旧失败。证据路径必须是项目内真实文件。修改成果后不能复用已失效证据，应重新打开任务并重新验证。

## 其他操作

```json
{"revision":1,"op":"reopen","task":"T20","reason":"已确认调整规则范围，需要复查下游内容"}
```

reopen 归档目标与其真实依赖任务的当前证据，目标设为 pending，下游设为 review（待复核）；无关任务保留，尚未开始的下游不制造历史记录。真实依赖由任务 depends、配置 dependencies 和检查点的本阶段成员共同确定；若发现漏依赖，先补齐并说明影响。保留旧证据文件及发行快照。

```json
{"revision":2,"op":"add","item":{"id":"T52","stage":"S5","title":"第二批事件","goal":"实现内容矩阵中已确认的第二批事件并验证","depends":["T41"],"required":["document","editor"],"instructions":"项目记录/当前操作/T52_第二批事件.md"}}
```

新增 ID 用英文字母、数字和连字符；同阶段依赖不能成环，不能依赖更后阶段。新增任务要附对应详细任务单和操作卡；所需文件须由 AI 按实际目标先创建。add 自动重开本阶段检查点及其真实下游；无关任务不重开。新增制作任务最低 document，AI 按风险增加实际测试。T50 要等所有内容批次完成，批次不能反向依赖 T50。

```json
{"revision":3,"op":"resolve","feedback":"F3","resolution":"已读取客户原话，更新规则 DEC-002 并安排 T52 验证；不是测试通过"}
```

反馈处理后明确答复客户并同步需要变动的权威文档。网页只允许追加反馈，不能直接伪造已验收任务，也不会把反馈自动发给模型。问题反馈先等待核实，不自动重开任务。关联任务显示待核实且不能作新的验收依据；AI 核实后决定修复、改需求或解释原设计。确需变更才 reopen，resolve 必须记录处理依据。想法或普通体验不自动作验收。

## 存储与恢复

写入使用本地互斥锁、revision 冲突保护、临时文件替换，并在 `项目记录/backups/` 留存更新前副本。锁持续存在时先确认原进程已结束，再由 AI 处理；不要让客户盲删。文件损坏会显示错误并阻止更新，不自动重置。

恢复时先停止服务，备份当前目录，选择明确版本的副本还原，执行 validate 再启动。恢复进度 JSON 不会同时恢复代码、资产和证据；整体恢复须使用同一时点的完整项目备份。网页导出仅是进度副本。

## 操作卡、证据修复与发行快照

update 支持 instructions（操作卡项目内路径）与 version（本轮版本）；进入 active/done 前必须有可读操作卡。已有关联证据时改变目标、依赖或操作卡须先 reopen；纯文件移动用 repair_reference。旧 schema 1 数据保留原状可读，缺操作卡在对应任务显示缺口，不自动补造证据。

validate 检查结构、路径边界和依赖，不因一个文件失效阻断全项目。show/API 同时给出 gaps、accepted、attention 与 effective_depends。done 是历史登记状态；accepted 才代表当前证据齐备，attention 提示历史验收需要核实。证据失效时仍可读取、导出、反馈、重开及修复。结构损坏则保留文件并走备份恢复。

```json
{"revision":4,"op":"repair_reference","task":"T00","old":"项目记录/旧日志.md","new":"项目记录/新日志.md","reason":"核对为同一原记录，仅移动文件"}
```

此操作只修引用并记录原因；内容变更必须重开与重测，不可以修路径名义替换证据。版本快照中的引用不会改写，原发行目录需稳定保留。

```json
{"revision":5,"op":"dispose_failure","task":"T31","index":0,"decision":"accepted_nonblocking","reason":"说明实际影响、可接受范围与后续安排","path":"项目记录/问题处置.md","by":"核实人","approval":"项目记录/客户确认.md","approved_by":"实际确认人"}
```

仅两类处置：not_applicable（需有明确不适用依据）与 accepted_nonblocking（额外要求客户确认文件）。未完成/阻塞缺陷不能伪装非阻塞。必需类别的最新结果仍必须 pass，不能靠处置绕过最低门槛。网页展示失败索引与处置路径。

```json
{"revision":6,"op":"snapshot_release","label":"1.0.1","by":"实际登记人","manifest":"项目记录/交付版本/1.0.1.md","publication":"local_delivery","tasks":["P101"]}
```

所有非 S9 交付任务和指定补丁任务须已验收且当前健康，版本号不得重复。publication 只允许 local_delivery 或 published，须与实际授权和结果相符。releases 保存当时任务副本，后续重开不改写；原包、源码、证据另行按版本备份，不把 JSON 快照当完整备份。示例路径与记录均须先用实际成果替换。
