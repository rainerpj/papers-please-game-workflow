# 交付维护与求助

S7–S9 按已确认平台和发行方式生成实际操作卡。平台未确定时不编造点击步骤、账号或费用；需要时查当时官方资料。以下是产出与顺序，不能直接冒充执行记录。

## 从发布候选到交付

1. 程序 skill 按真实工程构建完整可运行目录，写明版本号、目标系统、构建设置、输出目录和启动文件。客户收到整个构建包及说明，不能只复制一个 exe。源码工程与可运行包分别说明用途。
2. 从独立目录解压/安装，在约定设备按操作卡启动；验证新游戏→教学→工作循环→结算→保存退出→重启读取→结局。分支测试给明确入口和选择，不要求客户重复漫无目的玩全流程。记录设备、分辨率、版本、步骤、结果与日志，未测环境明确列出。
3. 先备份实际存档再测试升级；存档位置由代码或运行验证确定，禁止猜路径。对旧存档读入、继续、再次保存和回滚兼容逐项检查。不可逆存档迁移时保留旧包和旧存档副本并写明限制。
4. 按 [交付版本清单模板](../05_项目模板/交付版本清单.md) 生成对应版本清单，包含运行包、源码、项目记录、安装/操作说明、许可来源、已知非阻塞问题、反馈入口与维护范围。完成一次隔离副本的恢复演练：在新目录按清单恢复，能读记录、打开工程或运行包；只复制文件不算恢复测试。
5. 客户体验与完整范围通过后，先交付可审阅本地包。需要上传/上架时明确账号、渠道、接收人/受众、文件版本、商店文案、费用和操作授权；已有授权继续执行，不重复确认。只做本地交付就明确“未上架”。
6. 用 snapshot_release 记录版本快照和清单路径。快照不保存二进制文件，仍需完整版本归档；以后任务改变不覆盖历史版本。上架、交付、演练各用真实证据登记。

## 一个补丁怎样完成

收到问题 → 定位用户版本和复现步骤 → 判断影响/是否确需改动 → 在 S9 新增对应版本任务 → 修复 → 两轮审查 → 原问题复测与实际依赖回归 → 重新构建、独立运行与旧存档验证 → 客户验收 → 在授权内交付 → 归档新版本。

补丁任务注明旧版本、目标版本、问题 ID、改动范围、受影响系统/内容/存档、测试清单和回滚办法。至少为有代码改动的补丁要求 document/editor/build/player，涉及体验变化补 customer；风险需要时补 automated。其他任务依赖真实需要的前置，不把全部旧工作重新做一遍。用 snapshot_release 的 tasks 明确包括补丁任务。扩展故事规模则重新校准范围并新增制作任务。

阻止启动、丢存档、结局不可达等问题优先处理；不清楚是不是 bug 时先对照已确认规则，再解释预期与实际差异。客户接受非阻塞问题必须有范围、风险、理由及确认记录；不能接受阻塞缺陷来绕过发布门槛。

## AI 卡住或需要真人帮助

同类失败连续两次且没有新证据，或缺少账号/设备/文件访问时，不再循环试错。保留最后可用成果，更新 `docs/CODEX_HANDOFF.md`，包含：客户要达到的结果、当前现象、准确版本与路径、最小复现、错误日志、已试办法及结果、尚未验证项、需要谁提供什么。

客户只需转述：“请按这份交接继续排查，先复现，不要从头重做。”AI 给出可继续的独立工作；若确需外部开发者、付费服务或客户本人登录，说明具体缺口、交接范围和预计投入，由客户决定。未经授权不联系第三方或上传工程。

## 停下来再继续

阶段暂停时记录当前版本、未保存内容、下一步操作和阻塞。恢复时先检查实际文件、状态与备份日期；进度 JSON 恢复不会恢复代码、资源和存档。不要用较旧进度覆盖更新成果，也不要自动将历史通过当成新版本通过。
