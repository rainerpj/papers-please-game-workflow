# 用同类游戏帮助当下判断

这项能力贯穿完整生命周期，不是只在立项时交一份竞品报告。读当前问题、已确认需求、`项目记录/竞品参考记录.md` 和 `02_工作流规范/持续竞品参考.md`；不重新询问已确定类型，不复制其他游戏的整套设计。

## 触发与研究

客户表达“我不知道该怎么做”“不够紧张”“故事没融进去”“界面乱”“画面不像同一种风格”，或 AI 发现规则、叙事、制作成本冲突时，先把它转成一个可研究的问题。比如“玩家要在几处看日期，怎样让查找清楚但不失去判断乐趣”。

1. 先复用项目内已经查证的记录；版本、范围不匹配则补查。通常围绕一个问题选 1–3 个直接相关案例，不列无关大榜单。
2. Papers, Please 是已知主参考；其他作品由当前问题决定，不预设一定适合。先找官方说明、开发者讲解/演示；细节用可定位的实际试玩或公开视频核对。记录链接、访问日期、版本/平台、时间点或章节。
3. 不把商店标签推成精确机制，不声称看过未打开的视频、玩过未运行的游戏。分开：观察事实、设计意图推断、对本项目的建议。联网不可用时标待查证，不杜撰结论。
4. 对照客户目标、交互方式、内容成本、已确认范围说明可借鉴处与不适用处。销量与评价等易变数据若不是当下决策所需就不收集。

## 形成行动

给客户的输出应简短具体：“这款游戏在这个场景怎样做 → 玩家因此感受到什么（推断需说明）→ 我们可以怎样调整 → 会多出哪些工作”。一般给 2–3 个真正不同的方案，并明确推荐理由。

- 低成本、可逆、符合已批准方向的实现细节：AI 自行选择并记录。
- 改变主要体验、内容规模、题材或成本：向客户提出一个聚焦选择，继续无依赖工作。
- 需要体验才知道：提出最小对照实验，写观察标准与停止条件；不把研究意见当验收。

将采用/调整/拒绝/待实验与对应需求、任务 ID、证据写入参考记录。只有确认采用的规则进入游戏设计；研究完成不等于功能实现。测试后回填是否适用，避免下次重复争论。检查是否存在断章取义和不必要调研。
