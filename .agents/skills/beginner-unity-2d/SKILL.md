# Unity 2D 开发与交接

先读根目录 `AGENTS.md`、当前功能任务和已确认设计。检查实际 Unity 工程、Git 改动、`ProjectVersion.txt`、包清单、源码和代表调用；工作流目录不是 Unity 工程。不确定 API 时核对目标版本官方文档，不让客户选择架构。

## 实现

1. 明确本次玩家能看到的变化、输入/输出、状态真值、失败与清理、验收用例。小修直接处理；复杂改变先形成可审阅方案，尊重已有授权。
2. 查已有共享能力和调用者，优先沿用。分开内容定义、运行状态、规则执行与界面表现。审核规则尽量用可测试的普通 C#，Unity 组件负责生命周期与展示。不默认引入全局事件总线、单例框架或依赖注入。
3. 关注重复判决、重复结算、拖拽/点击冲突、日切换、暂停、退出、重新开始、规则快照、存档版本和旧存档迁移；按当前改动选择实际会发生的路径。
4. 保持 `.meta`、GUID 和已有 Scene/Prefab 引用。共享配置不可承载单局可变状态。事件订阅、临时对象和异步回调有明确释放责任。
5. UI 标签、文字与错误信息面向玩家；开发信息进入日志。资产生成提示词与视觉验收交给美术技能；互动不确定时主动参考同类游戏，不凭工程方便改变体验。

## 客户需要操作编辑器时

AI 能可靠完成的装配自行完成。无法直接操作时，交接必须写：实际或待创建资产路径 → 场景对象层级 → 组件 → 准确字段/值/引用 → 事件目标与方法 → 操作 → 预期画面。明确编辑基础 Prefab 还是实例；避免 Inspector 与代码重复绑定。给出一小段步骤，待结果回来再继续，不丢给客户“接一下引用”。

## 验证和完整产品

按改动执行规则自动测试、Unity 编译、Play 验证、Player 构建和独立运行；存档/输入/分辨率影响必须在对应环境确认。普通 C# 或静态检查不等于 Unity 通过。正式版本同时核对启动、继续游戏、设置、退出、完整内容与结局，不能因单一原型可玩就关单。

完成后先做正确性审查，再单独审查新增层次、字段、缓存、重复判断是否有当前消费者和必要性。追踪真实调用链。修复后复测受影响路径，证据写明版本、命令或步骤、结果、日志位置、未覆盖范围；同步进度。

## 新手操作与发行衔接

首次搭工程先读 `02_工作流规范/首次准备与能力预检.md`；按真实版本和工具能力创建可执行卡片，不预造 Assets 路径。每个制作任务遵循 `02_工作流规范/当前操作卡与内容生产.md`。美术音频接入与对应 skill 协作，验证真实文件与游戏行为。S7 后按 `02_工作流规范/交付维护与求助.md` 生成实际构建、独立运行、存档升级和恢复步骤。补丁独立任务要求相称的 editor/build/player 等证据，不能用早期版本运行记录验收新代码。
