# 新手游戏制作引导

在此交付包根目录工作。先读 `AGENTS.md`、`项目记录/state.json` 和当前需求。跨对话读 `docs/CODEX_HANDOFF.md` 并核对源码、资产、记录的新旧，不照搬历史结论。流程详见 `02_工作流规范/全流程与阶段验收.md`。

## 每次接手

首次进入或客户补充资料时，先读 `02_工作流规范/已有资料接收与理解.md`，清点当前对话附件和 `00_客户资料/`。核对 `项目记录/资料接收与理解.md`，先阅读尚未处理的资料、提取已有决定和来源，再继续访谈。已存在的文档不可要求客户重写；看不到附件需明确缺口，不声称已读。没有资料也允许继续，不把可选输入变成永久阻塞。

1. 识别客户是在继续任务、反馈问题、改想法还是询问情况；新消息通常补充当前任务，不自动取消它。
2. 已知类型是 Papers, Please 式审核游戏。查明当前阶段最早未完成任务、依赖、未处理反馈和已确认决定。不要让客户重新选类型。
3. 用一句话说清当前目标和本步可看到的成果。任务应在一次可验收的小循环内推进；总范围仍覆盖完整游戏。
4. 技术选择自己承担。影响体验/规模且未授权的选择，用具体情境和 2–3 个不同选项提问；同时将当前问题写入任务 question 字段，客户回答后记录决定并清空。其余工作继续。不会答时给一个可逆试验建议，记录为假设。
5. 按需要读取设计、程序、美术、参考或审查技能。引导与调度不等于启动子代理；仅有当前授权允许时委派。

## 竞品参考贯穿过程

客户说“不知道、太乱、没感觉、不像、选不出来”、设计互相矛盾、实现成本过大或体验测试失败时，主动判断能否从同类作品找到可观察的办法。读取 `beginner-game-reference/SKILL.md`。可以独立开展聚焦研究，不等待客户专业地提出“竞品分析”。已有可信记录能回答时复用；查不到时如实说明。

## 推进与收尾

- 做完后运行正确性审查和单独的必要性审查，再执行适当验证。先处理发现，再同步受影响文档和状态。
- 使用 `04_本地进度网页/workflow.py apply --payload ...` 更新状态；协议见 `02_工作流规范/进度数据与同步约定.md`。读取实际证据，不把模板当成果。客户反馈不能自动转成验收。
- 一项任务结束后，简短说明“现在能做什么 / 验证到哪一步 / 还缺什么 / 下一步”。网页与对话必须一致。
- 若客户中断，留下可恢复的文件、当前阻塞和下一操作。不要为聊天长度主动切断任务。
- 若无法运行 Unity，不要求客户自己诊断技术问题。给出对应版本的准确点击步骤与观察结果；结果未回来时标记待验证。
- 打包候选不等于已发行；交付安装包、正式上架、维护交接各自保留证据。后续版本继续新增任务与回归，不擦除前版历史。

## 结束条件

本步只在已约定成果、审查和验证齐备时验收。完整项目须通过完整范围、内容矩阵、全流程、目标环境、交付与维护阶段；禁止将原型或代表片段标为完整交付。

## 走查后的执行衔接

- T00 或迁移环境时读 `02_工作流规范/首次准备与能力预检.md`，完成真实读写、网页同步、客户反馈与答复的小闭环。没有客户结果就保持待验证。
- 每个任务进入 active 前按 `02_工作流规范/当前操作卡与内容生产.md` 生成本步卡片并登记 instructions；阶段检查点先拆实际批次，不把几十个事件作为一次客户动作。
- S2/S4 读 `02_工作流规范/范围估算与制作校准.md`，先给带依据的完整体验选项，代表片段后测成本再确认批量范围。
- 发布和维护时读 `02_工作流规范/交付维护与求助.md`，生成实际交付、恢复与补丁操作包，按版本归档。两次同类失败无新证据时整理交接，不能无限重复尝试。
- 使用 effective_depends/accepted/attention 判断下一步。反馈先核实；只有确认变更才沿真实依赖重开，已交付快照保留。
