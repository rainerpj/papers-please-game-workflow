# 改进记录操作协议

在项目根目录运行 `python 04_本地进度网页/improvement.py show`，查看 revision 后用 `apply --payload 项目记录/本次改进操作.json` 提交。客户无需编辑 JSON。本机优先共享 python.ps1；客户机器使用已预检解释器。以下是格式示例，必须替换真实来源和证据；各例 revision 是占位，不是可连续执行的脚本。

改进文件与游戏 state 使用同一写锁，revision 各自独立。旧包无改进文件时读取为空，首次受校验更新落盘；结构坏了不会重置。路径为项目内相对路径。备份在 `项目记录/backups`；每次改动的前后内容在 `项目记录/工作流改进证据/变更备份`，不注册为浏览器可下载证据。

## 捕获与核实

网页原反馈只保存在 state.json，执行同步后读取原文，不把“索引已同步”当作“原因已判断”。

```json
{"revision":0,"op":"sync_feedback"}
```

用宿主真实返回的对话/条目标识作为 key；没有标识时用项目内记录路径和段落位置。摘要明确 text_kind=summary。每个 stream 只覆盖本项目一个可解释来源范围，cursor 是实际读到的位置。

```json
{"revision":1,"op":"ingest","stream":"本项目对话A","from_cursor":"","cursor":"实际条目ID","coverage":"partial","note":"本轮只读到最近三轮，较早历史尚不可见","entries":[{"key":"对话A:实际条目ID","locator":"本项目对话A/实际条目ID","text":"客户明确说的原话或标注摘要","text_kind":"quote","at":"2026-11-10T00:00:00+00:00"}]}
```

覆盖为 complete/partial/unavailable；complete 只指声明的本次范围。unavailable 时 entries 为空、cursor 不推进。重复 key 内容一致则去重，不一致则拒绝覆盖；需要更正时创建新事件。读取位置和新信号一并原子写入，revision/from_cursor 冲突后重读。

```json
{"revision":2,"op":"record","key":"先读已有资料再提问","title":"减少重复询问已有设定","signals":["对话A:实际条目ID"]}
```

返回 I1 等编号。相同主题的候选项合并；已有核实结论后出现新来源会回到待核实；已进入试用或结束后出现新来源会建关联的新候选，保留旧效果历史。同一来源重读不产生新项。信号未归因前不要删除原记录。

```json
{"revision":3,"op":"assess","item":"I1","classification":"workflow","cause":"实际查明的原因","expected":"下次可观察的行为","case_path":"项目记录/工作流改进证据/案例-I1.md"}
```

classification 为 workflow/preference/game_requirement/environment/positive/uncertain。只有 workflow 或明确的协作 preference 可进入自动修改。其他项记录转交或暂缓：

```json
{"revision":4,"op":"decide","item":"I1","status":"dismissed","reason":"这是本次游戏美术方向变化，已转入需求记录，不能成为永久工作流禁令"}
```

status 可 deferred/dismissed。暂缓后可重新 assess；已实际修改不能绕过恢复而直接 dismissed。

## 备份、修改与验证

```json
{"revision":4,"op":"prepare","item":"I1","files":[".agents/skills/beginner-game-guide/SKILL.md"]}
```

prepare 只备份、不执行修改。允许本项目 skills、客户指南、规范、模板、提示词、docs 及非核心网页工具。AGENTS.md、workflow.py、workflow.json、improvement.py、server.py、Game 和项目记录不在自动修改范围；涉及核心协议时走单独方案与受控实施，不绕过保护。工具不能替代对 AI 手工改动范围的审查。

核对现有未完成修改后实际编辑指定文件；改完先封存：

```json
{"revision":5,"op":"seal","item":"I1"}
```

seal 登记修改后内容，保持 editing；验证失败也能在此基础上回退。封存后不继续修改同一项；需要改进可回退后创建关联新项。断在 prepare 后，可先核对文件、seal 已发生的本次修改，再恢复。如果完全没改，使用 `{"revision":5,"op":"cancel","item":"I1","reason":"实际取消原因"}` 结束准备；工具会核对所有文件仍与备份相同，已有修改不能走此捷径。回退后再次尝试时，以新的验证失败记录或观察作为来源创建关联改进，不复用旧来源虚增条目。

```json
{"revision":6,"op":"trial","item":"I1","validation_mode":"scenario_review","checks":{"correctness":{"result":"pass","path":"项目记录/工作流改进证据/验证-I1.md","note":"实际检查范围与结果","by":"执行人","at":"2026-11-10T00:00:00+00:00"},"necessity":{"result":"pass","path":"项目记录/工作流改进证据/验证-I1.md","note":"单独检查必要性与规则冲突","by":"执行人","at":"2026-11-10T00:00:00+00:00"},"original":{"result":"pass","path":"项目记录/工作流改进证据/验证-I1.md","note":"原失败情境的实际结果","by":"执行人","at":"2026-11-10T00:00:00+00:00"},"related":{"result":"pass","path":"项目记录/工作流改进证据/验证-I1.md","note":"相近情境与原有有效行为的结果","by":"执行人","at":"2026-11-10T00:00:00+00:00"}}}
```

validation_mode 为 automated/scenario_review/fresh_context，分别是自动测试、同一 AI 情境自查、新上下文行为验证；按实际执行填写。四项都须通过，案例和记录存在且读取过，封存后的文件没有又改变。工具检查结构与文件，AI 负责内容真实性。

## 效果与恢复

```json
{"revision":7,"op":"observe","item":"I1","outcome":"effective","observation":{"kind":"usage","path":"项目记录/工作流改进证据/观察-I1.md","note":"后续相似情境中实际发生了什么及限制","by":"执行人","at":"2026-11-11T00:00:00+00:00"}}
```

outcome 为 effective/ineffective；kind 为 usage/customer。观察时间不得早于 trial，原验证仍需可读取，规则须与封存版一致。未遇到相似场景不调用 observe，保留 trial；“没再抱怨”不算证据。

```json
{"revision":8,"op":"rollback","item":"I1","reason":"实际反效果或验证失败，撤回这次改动"}
```

工具在写文件前核对全部改动文件仍等于封存后的内容；有任何后续修改则全部拒绝覆盖，AI 需按差异人工合并。只还原登记文件：原有文件恢复，新建文件撤销；不回退整个游戏状态或其他成果。先落盘 reverting 恢复日志，执行中断后读取新 revision 再执行同一操作即可继续；已恢复内容允许保留。不要删除恢复日志来解除冲突。

## 复盘与频率

```json
{"revision":9,"op":"review","scope":"task","game_revision":1,"note":"已核对本步纠正、返工和待观察项；没有新增问题时如实记录或跳过"}
```

scope 为 task/cycle。task 标记任务收尾读到的游戏版本，不重置集中复盘计数；cycle 登记本次集中复盘覆盖的游戏版本和信号数。game_revision 必须与当前一致。先处理/暂缓本次来源并写明限制再登记，不用 review 隐藏未读材料。

show 显示新任务完成事件、阶段验收、每 5 个完成事件、7 天且有新材料的复盘提示，以及尚未核实的开放反馈。V0.3 以前没有 completed 字段的历史事件不猜测完成时间，首次接手人工核对历史覆盖。长期未启动时在下一次对话补查，不声称后台已执行。

```json
{"revision":10,"op":"policy","tasks":5,"days":7}
```

若网页反馈实际属于协作问题，由 AI 使用 workflow.py 分类，避免影响游戏验收，保留原话和分类原因：

```json
{"revision":1,"op":"route_feedback","feedback":"F1","scope":"workflow","reason":"已核实为操作说明不清，而非游戏功能错误"}
```

反馈答复后用 resolve；这只代表反馈已受理/答复，不代表改进已被实际证明有效。需要记录游戏缺陷时 scope=task 并填写真实 task。
